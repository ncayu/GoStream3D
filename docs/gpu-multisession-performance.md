# Windows GPU 多路性能验证

## 行为

2026-10-04 已增加可配置的画面策略、统一 GPU 帧率预算和逐路反馈。以下 2026-10-03 测试数据属于当时的固定策略；新版本行为与测量范围见 [多路优化说明](multistream-optimization.md)。

- 每位观看者分配独立的 Chromium/Edge 实例、WebGL 场景、输入和 JPEG/WebSocket 画面流；不共享镜头或鼠标。
- 已预加载但无人观看的 GPU 实例停止截图编码，并申请约 2 FPS 的动画预算。交互优先项目被动观看时申请约 6 FPS；持续动画项目在观看期间一直申请目标帧率。首次接入或有输入时申请项目目标帧率，所有 GPU 实例共享可配置预算，并根据有效的帧率/延迟反馈调整。3 秒没有新画面才恢复停滞的 screencast。
- 观看页标签隐藏后，不再为该观看者送帧；如果该实例没有其他可见观看者，则停止截帧。标签切回时通知其 Worker 恢复截帧、解除动画节流，并重置 FPS 统计窗口，避免把后台时段算进当前显示帧率。
- 这是资源调度，不是硬件编码。Windows 本机模式仍是 JPEG/WebSocket；任务管理器的 Video Encode 为 0% 属于当前传输实现，GPU 3D 使用率不能单独说明截图、JPEG 编码、网络和客户端解码的瓶颈。

## 2026-10-03 现场验证

设备为 RTX 3050 Ti Laptop GPU（4 GiB 专用显存），项目“示例项目 A”，3 个独立预加载实例，1920×1080。用 `tools/three-stream-fps-probe.cjs` 同时建立三条观看连接并持续拖动第一路；每个值是在预热 2 秒后统计的服务端 WebSocket 实际 JPEG 到达帧率。

| 实现阶段 | 第一路 | 第二路 | 第三路 |
| --- | ---: | ---: | ---: |
| 原实现，操作期间每 250 ms 重启截帧 | 12.8 FPS | 1.9 FPS | 2.2 FPS |
| 仅在连续 3 秒无新帧时恢复截帧 | 13.5 FPS | 6.1 FPS | 6.3 FPS |
| 再加无人观看停止截帧 | 12.7 FPS | 12.7 FPS | 12.4 FPS |
| 再加被动观看约 12 FPS 动画调度 | 14.0 FPS | 11.3 FPS | 11.5 FPS |
| 被动观看约 6 FPS，先操作第三路再切回第一路 | 23.2 FPS | 5.9 FPS | 6.2 FPS |
| 被动观看约 6 FPS，三路同时持续拖动 | 12.3 FPS | 12.7 FPS | 12.5 FPS |
| 另两路观看标签隐藏，仅第一路持续拖动 | 34.4 FPS | 0 FPS | 0 FPS |

前一阶段“先操作第三路，再回到第一路”复测时，第一路为 14.8 FPS，另两路约 10.9、10.7 FPS；将被动动画调度改为约 6 FPS 后，切回第一路达到 23.2 FPS（最终构建复测 23.4 FPS）。代价是其余仅观看而未操作的会话约 6 FPS；每一路一旦接收到输入，就立即恢复原始动画速率。三路同时持续操作时各约 12–13 FPS。若三条观看连接在同一浏览器的不同标签中，隐藏的两个标签不需要接收画面；仅第一路可见时测得 34.4 FPS，模拟“第三路隐藏后切回第一路”测得 33.4 FPS。无人观看时三个原始场景的动画帧率均约 2 FPS；一次 `nvidia-smi` 采样为 GPU 24%、显存 3084/4096 MiB。实际帧率会随场景镜头、背景程序和驱动变化。

这些数字仍未达到 30/60 FPS 的流畅视频目标。此设备在三路满负载时可能达到 GPU 100%；当前 JPEG 截帧还需要浏览器将画面读回并编码，增加项目目标 FPS 不会消除此开销。若必须让三位用户在原始画质下同时获得 30/60 FPS，应在目标设备上评估支持硬件视频编码的低延迟传输（例如 WebRTC）和更多 GPU/显存容量。不能把任务管理器某一时刻 30% 的 GPU 3D 使用率直接推断为还有两倍以上的可用帧率。

## 回归命令

在服务仅运行目标项目且预加载 3 路就绪时：

```powershell
node tools/preload-live-check.cjs status
node tools/three-stream-fps-probe.cjs 12000 3 switch-back
node tools/three-stream-fps-probe.cjs 12000 3 all-active
node tools/three-stream-fps-probe.cjs 12000 3 one-visible
node tools/three-stream-fps-probe.cjs 12000 3 tab-switch
node tools/live-frame-probe.cjs
```

浏览器集成测试需要可启动真实 Edge/Chrome 的 Windows 环境。三个 3D Worker 已运行时再跑浏览器集成测试可能超出 4 GiB 显存，应在停止服务或空闲环境中执行。

## 2026-10-03 当前设备容量复测

用户询问 RTX 3050 Ti Laptop GPU（4 GiB 专用显存）最多能跑多少路。测试时总通道设置为 3，项目“示例项目 A”的观看配额为 6、预加载为 3，分辨率 1920×1080，目标配置 60 FPS。保持原有 CPU 使用上限 85%，不修改通道或项目配置。每次启动三个独立实例，预热后分别让 1、2、3 位观看者持续拖动 12 秒，统计预热前 2 秒之后 WebSocket 收到的真实画面帧；结束后恢复项目暂停。两轮测试结果：

| 同时交互人数 | 第一轮各路实际 FPS | 第二轮各路实际 FPS | GPU 峰值 | 显存峰值 |
| --- | --- | --- | ---: | ---: |
| 1 路（另 2 路已预加载） | 33.1 | 31.4 | 100% | 3530–3616 MiB |
| 2 路（另 1 路已预加载） | 16.5 / 16.8 | 16.0 / 16.1 | 100% | 3579–3648 MiB |
| 3 路 | 13.1 / 13.1 / 7.9 | 13.5 / 13.3 / 8.2 | 100% | 3562–3613 MiB |

无用户观看、三个实例完成预加载后，第二轮 GPU 约 3%、显存 3501/4096 MiB；当前电脑其他程序在项目启动前已占约 1.7 GiB 显存。第三路低于 10 FPS 的现象在两轮中重复出现。Windows 本机 JPEG/WebSocket 传输不使用 NVENC，`nvidia-smi` 的 Video Encode 为 0%；GPU 峰值 100% 表明不能根据空闲时的平均 GPU 使用率推断还能线性增加路数。

**报告口径：**当前软件配置最多允许 3 路同时运行，且已验证 3 路都能进入、独立交互；但三路同时操作时第三路仅约 8 FPS，不能将“可启动”称为“流畅”。若希望各路至少约 15 FPS，此场景建议最多 2 路；若希望约 30 FPS，建议 1 路。4 路及以上没有在这台设备上做稳定性验证；当前通道上限已阻止开启第 4 路，且三路已用约 3.5–3.6 GiB 显存并达到 GPU 100% 峰值，不应声称 4 路可用。不同镜头、分辨率、后台程序和驱动会改变结果。复现工具 `tools/gpu-capacity-report.cjs` 会在目标项目原本暂停且通道空闲时测试，并在结束时恢复暂停；详细原始样本保存在 `.cache/gpu-capacity-report.json`。
