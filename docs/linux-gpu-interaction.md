# Linux NVIDIA GPU 交互优化与实测记录

日期：2026-10-09。交付版本：`20261009-221512`。

已修复视频中的重复鼠标、滚轮方向及过大的滚动幅度，并优化输入调度和 NVIDIA 编码等待。服务器 `192.168.1.100` 已升级，原项目恢复运行。观看页请按 **Ctrl+F5** 强制刷新；仅等待连接恢复不会加载新版本的前端代码。

## 问题原因与修改

### 两个鼠标

观看端有本地鼠标，远端视频又捕获了一个鼠标。虽然自定义管线曾设置 `show-pointer=false`，Neko 3.1.5 在自动生成 legacy 视频管线时会将它改成 `true`，实际观看连接使用的就是 legacy 管线。

现在通过 `NEKO_CAPTURE_VIDEO_PIPELINES` 显式配置 main 和 legacy 两条管线，均设置 `show-pointer=false`，只保留观看端实时响应的本地鼠标。实机日志已确认两条管线都关闭鼠标捕获。

### 滚轮方向相反、缩放幅度异常

DOM 的 `deltaY` 正值表示向下滚动，Neko 旧二进制协议中的正值表示 X11 向上滚动。原来直接发送像素增量 `120`，远端会执行 120 次滚轮按钮操作，而不是一次。原有 80 毫秒节流还会丢弃连续滚动输入。

现在按像素、行、页三种单位转换为滚轮步数，反转协议方向，累计小幅输入，并保留完整的反向操作顺序。每次发送最多 16 步，剩余步数后续发送。普通像素模式下，累计 100 像素转换为一步；这是交互灵敏度选择，不是浏览器对所有鼠标设备的统一规定。

实机输入 `deltaY=+120`、`deltaY=-120`，远端页面依次收到 `+120`、`-120`，不再反向或放大成上百次滚动。修复遵循远端页面自身的缩放规则，不改写 ThingJS 场景代码。

### 交互延迟

- 鼠标移动按动画帧合并，只发送最新坐标；发送缓冲区积压时保留最新位置，避免排队播放过时移动。按下和松开仍使用可靠传输，并先定位到当前坐标。窗口失去焦点时释放按键。
- 观看端仅将视频轨道放入显示流，避免静音播放器等待不使用的音频播放同步。支持时设置接收端 `jitterBufferTarget=0`，旧浏览器尝试 `playoutDelayHint=0`。这是低延迟提示，浏览器仍可为网络抖动保留缓冲；测试中仍能观察到音频 RTP 包，不能据此声称完全停止音频传输。
- NVIDIA H.264 编码显式设置 `preset=p4 tune=ultra-low-latency rc-mode=cbr`，关闭 B 帧和 lookahead，VBV 容量按两帧码率预算配置。30 FPS、6000 kbps 时为 400 kbit。原始帧队列只保留最新一帧，编码输出关闭时钟等待；没有主动丢弃已经编码的参考帧。

保持项目的分辨率、帧率设置及原来的 6000 kbps 码率，未缩小到 720p。低延迟编码参数可能改变画面压缩细节，应结合实际场景检查画质。

参数定义见 [GStreamer nvh264enc 官方文档](https://gstreamer.freedesktop.org/documentation/nvcodec/nvh264enc.html)，浏览器缓冲提示见 [W3C WebRTC 标准](https://www.w3.org/TR/webrtc/)。

## 实机证据

服务器为 WSL2 Ubuntu，GPU 为 NVIDIA GeForce RTX 3050 Ti Laptop。WebGL 探针在测试画面及真实园区页面均返回：

```text
ANGLE (Microsoft Corporation, D3D12 (NVIDIA GeForce RTX 3050 Ti Laptop GPU), OpenGL 4.6)
```

Neko 实际运行 `nvh264enc` 管线，观看端接收 `video/H264`。这同时检查了浏览器绘制、编码管线和观看端接收，而不仅是 `nvidia-smi` 能否运行。

### 点击到视频变化

测试使用同一个 1920×1080 / 30 FPS WebGL 颜色切换画面。在观看端发送点击后，通过视频帧像素读取判断画面颜色变化。每轮 14 次点击，排除前 2 次预热，统计 12 次。数值是浏览器检测到返回视频变化的时间，未包括物理显示器扫描时间。

| 测试 | 平均延迟 | 最小 / 最大 | 视频中的远端鼠标白色像素 |
| --- | ---: | ---: | ---: |
| 修改前 | 76.9 ms | 67.4 / 86.2 ms | 48 |
| 仅更新前端 | 76.7 ms | 72.6 / 81.4 ms | 48 |
| 前端与服务器完整更新 | 61.5 ms | 55.8 / 68.1 ms | 0 |

完整更新这轮平均减少 15.5 ms，约 20%。前端单独更新没有明显改善该简单画面的平均延迟，也不能解决旧服务端捕获鼠标的问题。三轮均无页面脚本错误。该短时实验说明这一测试条件下的改善，不代表每个复杂 3D 场景、网络和终端都有相同比例收益。

### 真实 3D 园区

使用独立临时项目，加载真实园区场景，预热 30 秒，然后分五段持续采样，每段约 6 秒并执行拖动。原项目仍在运行，未用测试操作改变原项目视角。

- 分辨率：1920×1080；设置帧率：30 FPS。
- 平均播放帧率：27.22 FPS；五段分别为 28.22、26.86、27.28、27.75、26.00 FPS。
- 视频：H.264；采样期间解码丢帧 0，RTP 丢包 0。
- 截图确认实际园区已加载并随拖动改变视角。

本轮没有对同一园区负载做旧版同步 A/B，因此不声称真实场景帧率提高了多少，也不保证 60 FPS。WebRTC 的累计 `jitterBufferDelay` 不等于输入到画面延迟；应除以对应输出帧数并区分采样区间。指标定义见 [W3C WebRTC Stats](https://www.w3.org/TR/webrtc-stats/)。
