# Linux 纯 CPU 渲染优化与实测

2026-10-09，北京时间。交付版本：`20261009-135344`。

后续调整：按用户要求，已撤回 CPU 自适应 720p 上限，保留视频编码优化。以下为 `20261009-135344` 的历史测量记录；720p 结果不代表撤回上限后的当前默认行为。

继续优化有价值。本次服务器测试中，旧版 1080p 平均播放帧率为 17.02 FPS，新版自适应 720p 两轮平均约 23.80 FPS，提升约 40%。复杂园区场景的软件绘制仍占用大量 CPU，尚未稳定达到项目设置的 30 FPS。

## 实现

- 保留 Chromium SwiftShader 纯 CPU 绘制，无需启用核显或硬件编码。
- Linux CPU 自适应模式最大 1280×720，按窗口比例缩放。预加载、公开尺寸元数据、前端尺寸请求、服务端 WebSocket 限制使用同一上限；鼠标坐标仍依据实际视频尺寸换算。
- 显式固定 1920×1080 等分辨率继续有效。GPU 模式和 Windows 原生 JPEG 渲染不受此上限影响。
- Linux Docker 和 Linux 原生 Neko 两条路径均使用新版 CPU 视频管线：实时 VP8、2 个编码线程、`cpu-used=8`、量化范围 4–40、目标码率 2.5 Mbps、无前瞻帧。色彩转换前的原始帧队列只保留一帧，积压时丢弃旧帧。
- 视频采样帧率跟随项目设置。本次项目设置 30 FPS；旧版 Neko 默认视频采样为 25 FPS。因此 1080p 对比评估的是整条新版视频管线，包括采样帧率调整，并非某个编码参数的独立效果。

1280×720 的像素数为 1920×1080 的 44.4%。这减少了需要处理的像素，但不会同比减少模型遍历、JavaScript、顶点处理等开销。编码速度和分辨率的取舍可能降低细节，不能承诺所有场景达到 30/60 FPS。

## 测试方法

服务器：`192.168.1.100`，Intel Core i5-1135G7，4 个物理核心、8 个逻辑线程，约 31 GiB 内存。Docker CPU worker 为 `gostream3d/neko/chromium:3.1.5`；对比使用相同 worker，网关升级后注入新版视频管线。旧网关版本为 `20261009-132115`。

使用原项目相同的 ThingJS 园区 URL 创建临时项目。原项目始终保持停止状态。每轮停止并重新启动临时 worker，以重置场景；Windows Edge 接收端窗口固定 1920×1080。等收到至少 20 帧后再等待 5 秒，随后执行 5 次相同的鼠标拖动，每次取约 6.2 秒的视频统计，单轮测量约 31 秒。

播放 FPS 来自 `HTMLVideoElement.getVideoPlaybackQuality()` 的实际呈现帧数增量。解码、接收端丢帧和抖动缓冲统计来自 WebRTC `getStats()`。它们不是场景引擎内部绘制 FPS，也不是端到端鼠标响应延迟。不同分辨率的相同屏幕拖动对应相同窗口相对位移，但实际场景动画、负载和网络仍有波动。

## 原始结果

| 方案 | 实际视频尺寸 | 平均播放 FPS | 5 个采样区间 FPS 范围 | 接收端丢帧增量 | 平均解码 ms/帧 | 抖动缓冲平均停留 ms |
|---|---|---:|---:|---:|---:|---:|
| 旧版视频管线 | 1920×1080 | 17.02 | 6.11–22.48 | 224 | 5.66 | 956.20 |
| 新版视频管线，固定 1080p | 1920×1080 | 22.48 | 19.28–25.16 | 0 | 5.54 | 109.20 |
| 新版视频管线，自适应 720p | 1280×720 | 23.45 | 19.34–28.20 | 0 | 2.96 | 63.79 |
| 新版 720p，重启后复测 | 1280×720 | 24.16 | 22.96–27.24 | 0 | 2.97 | 24.15 |

计算方法：平均 FPS = 呈现帧数总增量 / 总采样时间；平均解码耗时 = `totalDecodeTime` 增量 / `framesDecoded` 增量；抖动缓冲停留 = `jitterBufferDelay` 增量 / `jitterBufferEmittedCount` 增量。FPS 范围是每个约 6 秒区间的平均值，不是瞬时最低/最高值。

旧版 `packetsLost` 曾短暂报告 8，后续回到 0；其最终净增量为 0 不能证明完全没有丢包，也不能排除网络、补包或接收端缓冲对结果的影响。此前只依据最终值判断“没有丢包”不充分。单轮旧版与两轮新版的结果支持本机本场景的改善，尚不是多机、多场景、长时间统计结论。

`docker stats` 的 100% 代表一个逻辑核心。新版 1080p 的观察值为 654.45% 与 721.41%；720p 第一轮测量期间为 642.15%、714.78%、691.23%，复测期间一次为 668.09%。旧版 665.76% 取于播放器关闭后。这些不是完整同步平均采样，不能据此宣称 CPU 降低了某个百分比；它们说明新版仍存在高 CPU 占用。当前优化主要改善交付帧率、接收端丢帧与缓冲，不等于消除了软件绘制瓶颈。
