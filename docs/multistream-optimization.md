# 多路调度、通道回收与 JPEG 测量

2026-10-04 增加逐路性能数据、可选择的 GPU 画面策略和观看请求优先的空闲通道回收。Windows 继续使用 JPEG/WebSocket，未启用视频编码，也未承诺特定的业务场景帧率。

## 使用配置

- “创建观看链接 / 编辑链接 → GPU 画面策略”：`interactive`（交互优先，默认）在无人操作时申请约 6 FPS，输入后的 3 秒内申请项目目标 FPS；`animation`（持续动画）在可见观看期间持续申请项目目标 FPS。无人可见观看时申请约 2 FPS，并停止截图采集。各路申请受全局预算约束。
- “后台设置 → 多路性能与空闲通道”：GPU 总帧率预算默认 120，可设 30–1200。该值是所有 GPU 实例的场景动画更新调度预算，不是 GPU 使用率硬上限，也不表示保证的显示 FPS。CPU 实例不使用此预算。
- 同处可关闭空闲回收。默认开启：只有真实观看请求遭遇端口池耗尽时，才尝试回收其他项目的空闲、已就绪预加载实例。后台预加载和定时维护不触发抢占。
- 项目内的“优先保留预加载路数”可设 0–`preload_count`，默认 0。回收保留这个下限，保护正在观看的实例；加载中、正在修改、清理失败的实例也不会被当成可立即复用的空闲槽。先回收额外备用实例，再考虑主实例。
- 重点项目的保留路数总和应不超过服务器总通道数。重启时先恢复有保留路数的项目。保留路数保护已预加载的实例，并不绕过硬件、加载错误或端口池容量限制。
- 回收后保留项目与链接，显示“空闲通道已让出”。自动恢复至少等待 1 分钟，并检查真实空闲通道和进行中的观看请求，避免回收后马上重新占满。重新访问该项目仍可按需启动或复用现有实例。

持久化文件：会话配置内增加 `frame_policy`、`reserved_preloads`；全局策略保存到会话目录旁的 `performance-settings.json`。旧会话自动补全为交互优先、保留 0 路。项目改变画面策略需要结束观看并重建 Worker，沿用原观看地址；全局预算与回收开关保存后立即生效。

## 反馈和预算

每 500 毫秒为所有 GPU Worker 计算统一的加权、封顶分配。交互、持续动画、被动观看、无人观看的权重分别为 3、2、1、0.25；未用满目标的路会让出剩余预算。低于 1 FPS 的份额依然为正数，避免把零传入页面调度器后变成不限帧。

客户端每约 500 毫秒反馈一个已显示帧。服务器验证此帧的发送记录后，更新解码、绘制与发送到显示回执的平滑耗时。反馈最近 10 秒内有效，并且最近 2 秒收到采集帧时，如果显示回执超过 250 毫秒、发送等待超过 50 毫秒，或解码耗时超过目标帧间隔，则将该路申请值限制到实测采集 FPS 的约 1.25 倍（上限仍为项目目标，保留不高于目标的 6 FPS 恢复空间）。反馈消失时回到正常需求，避免使用旧样本长期压低帧率。

实际帧率偏低本身不触发降速，因为静态页面、低更新频率、场景耗时和截图瓶颈均可能导致低采集 FPS。预算是软调度：各 Worker 应用新分配存在短暂延迟，也不能控制应用绕过 `requestAnimationFrame` 的计时器或其他 GPU 工作。

## 测量范围

“平台监控 → 逐路画面性能”每 3 秒读取 `/api/v1/admin/performance`，包含所有活动 Windows Worker。接口需要管理员认证。旧客户端默认只收到原有二进制 JPEG；新客户端先发送 `telemetry` 协商，然后接收帧序号元数据并发送 `frameAck`。反馈不会刷新交互优先级。

| 指标 | 实际测量范围 | 限制 |
| --- | --- | --- |
| 目标 / 调度 FPS | 项目目标；当前成功应用到 GPU 页面调度器的更新预算 | 不代表最终画面 FPS |
| 采集 FPS | 最近采样窗口中服务端有效 JPEG 帧的到达速率 | 包含采集与编码链路，静态画面可能偏低 |
| 显示 FPS | 客户端在最近统计窗口内执行绘制的速率 | 不等于显示器物理呈现次数；隐藏标签页停止绘制 |
| 截图时间 | `Page.captureScreenshot` 命令从发出到收到 JPEG 的总耗时 | CPU 截图回退时有样本，不能拆成独立读取和编码耗时 |
| 采集交付 | 浏览器 screencast 帧时间戳到服务端处理事件的耗时 | 包含浏览器采集、编码、CDP 传输与事件处理，不能称为纯 JPEG 编码耗时 |
| 服务端整理 | Base64 解码、JPEG 尺寸校验和帧状态更新的耗时 | 是轻量步骤，可能低于计时精度 |
| 发送 | WebSocket 写入元数据和二进制 JPEG 的耗时 | 表示写入与回压等待，不是远端确认收包时间 |
| 解码 / 绘制 | 客户端 `createImageBitmap` / `drawImage` 耗时 | 绘制调用返回不保证物理显示器已呈现 |
| 显示反馈往返 | 服务端发送帧至客户端绘制后回执到达的耗时 | 包括双向网络、解码、绘制和调度，不是纯网络 RTT |
| 丢帧 | 服务端满队列覆盖计数；客户端待解码帧覆盖计数 | 主动丢弃旧帧控制排队延迟，计数不是网络丢包率 |

采集交付指标使用 Chromium 的帧元数据墙钟时间戳，源端与服务端在同一 Windows 主机，不需要同步客户端时钟。字段来源参见 [Chromium PageHandler 的元数据和编码实现](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/devtools/protocol/page_handler.cc)。缺失或异常时间戳不参与采样。

## 实测与视频传输评估

已通过真实 Edge/Chrome 的小型 640×360 动画夹具检查策略应用与 JPEG/反馈链路；测试隔离于已保存项目，不修改正在运行的服务。该夹具验证的是传输与调度机制，不能作为复杂 3D 场景容量结论。客户端为 Go JPEG 解码器，夹具中的解码样本也不能代替浏览器实测。

本机夹具预热后的一个样本（两路目标均为 30 FPS；未模拟实际业务场景）：

| 策略 | 调度 FPS | 实测采集 FPS | 采集交付 | WebSocket 写入 | 显示反馈往返 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 交互优先，停止操作后 | 6 | 5.95 | 2.27 ms | 0.52 ms | 4.11 ms |
| 持续动画 | 30 | 28.94 | 2.03 ms | 0.26 ms | 3.53 ms |

此样本只证明两种策略在真实浏览器中产生不同的被动观看行为，不证明复杂 3D 场景能够达到 30 FPS，也不是优化前后的吞吐对比。

对真实业务应分别采集 1、2、3 路在静止、单路交互、同时交互、持续动画及标签页切换时的样本，每种状态预热后至少观察 30 秒。固定画质、分辨率、镜头、目标 FPS 与 CPU 配额。记录各路 FPS、各步耗时、丢帧、网络吞吐、显存、GPU 3D/Video Encode 和 CPU 使用率；先用低延迟局域网基线，再测目标客户端与网络。

视频 / NVENC 仍属于后续原型评估：在相同场景与画质下比较 JPEG 基线和低延迟视频原型的采集、编码、端到端反馈、带宽与多路公平性。必须先确认浏览器画面的捕获和编码路径、显卡编码能力与并发限制、客户端支持、WebRTC 拥塞控制和输入到显示延迟。只有目标环境测量证明收益后才应切换正式传输；GPU 使用率偏低以及“使用硬件编码”都不能作为帧率保证。

历史设备与业务场景样本见 [原多路性能记录](gpu-multisession-performance.md)，其中 2026-10-03 数字属于旧策略，未当作新策略的提升结果。
