# Linux NVIDIA GPU 大屏画质优化记录

版本：20261009-232907。目标服务器：192.168.1.100，WSL2 Ubuntu，NVIDIA GeForce RTX 3050 Ti Laptop，4 GB 显存。

## 为什么之前会糊

原 NVIDIA 编码管线固定使用 6000 kbps CBR。观看窗口变大到 2K、4K 后，像素数量增加，但编码预算没有同步增加，建筑细线、植被和运动中的纹理容易被压缩掉。此外，高 DPI 屏幕使用 CSS 尺寸请求渲染，会把较小的视频放大到物理屏幕尺寸。

本次沿用项目自适应分辨率，最高 3840×2160，没有缩小到 720p。GPU 观看端按物理像素请求画面，设备像素比最高 2；固定分辨率仍按项目选定尺寸运行，CPU 与 Windows 的尺寸规则保持原样。

## 编码参数

NVIDIA 使用 NVENC H.264 硬编码，改为 VBR，目标质量 `const-quality=20`，开启空间自适应量化 `spatial-aq=true aq-strength=6`。画面静止时不必持续占满码率，细节丰富或运动时可以使用更高预算。每次创建采集管线，包括自适应窗口调整后，均根据实际宽、高、帧率重新计算预算。

|实际分辨率 / 帧率|目标码率|峰值预算|VBV 容量|
|---|---:|---:|---:|
|1920×1080 / 30 FPS|18 Mbps|27 Mbps|1800 kbit|
|2560×1440 / 30 FPS|32 Mbps|48 Mbps|3200 kbit|
|3840×2160 / 30 FPS|72 Mbps|108 Mbps|7200 kbit|
|3840×2160 / 60 FPS|144 Mbps|216 Mbps|7200 kbit|

这些是编码预算，实际流量随画面变化，峰值也不等于网络流量的严格瞬时上限。多路观看需累加链路预算；4K 高运动场景应使用有充足余量的有线网络。无需为不动的画面强行填满码率。

继续使用 `preset=p4 tune=ultra-low-latency`、`bframes=0`、`rc-lookahead=0`、`zerolatency=true`；原始帧队列仅保留最新一帧，输出不等待时钟。VBV 按峰值预算的两帧容量设置，不引入 B 帧重排序。保留 constrained-baseline / NV12 以兼容现有观看链路。参数定义见 [GStreamer nvh264enc 官方文档](https://gstreamer.freedesktop.org/documentation/nvcodec/nvh264enc.html)。

## 客观画质对比

在同一 NVIDIA GPU 上，使用相同的 16 帧 1920×1080 / 30 FPS 动态 zone-plate 细线测试图，分别经过旧、新编码器，再解码到 NV12，逐像素比较亮度。

|指标|旧版|新版|
|---|---:|---:|
|亮度 PSNR|27.27 dB|37.62 dB|
|8×8 局部亮度 SSIM|0.97321|0.99751|
|测试码流平均载荷|3.32 Mbps|9.00 Mbps|

PSNR 提高 10.35 dB。测量仅隔离编码损失，SSIM 使用本次脚本的 8×8 局部实现；不能据此推断任意园区场景有相同幅度的提升，也不是色彩无损证明。H.264 / NV12 仍然是有损压缩，不承诺像素完全一致。

证据：随包 `quality-proof/codec-proof.json`、`before-detail.png`、`after-detail.png` 和完整亮度图。测试码流也随包保存，原始 NV12 帧在开发目录 `output/gpu-quality/quality-codec/`，没有放入安装包以避免无谓增大体积。

## 实机场景与交互验证

同一 ThingJS 园区、1920×1080、30 FPS 设置，各预热 30 秒，再分 5 段拖动画面，累计约 30 秒。目标服务器同时保留原项目的预加载实例，使用独立临时项目执行对比，结束后删除。

旧版平均播放 27.03 FPS，新版 27.43 FPS。画质预算增加后，本轮 1080p 帧率没有明显下降；场景自身绘制、显卡功耗、其他负载和网络仍会影响帧率，不能保证所有场景达到 30 或 60 FPS。

证据：`quality-proof/scene-before-1080.json`、`scene-after-1080.json`。其他分辨率与交互结果见下方实测记录及随包 JSON。

在同一个自适应测试实例中依次调整 1080p、2K、4K，检查真实视频尺寸。另一个原园区实例持续保留，期间原链接有实际观看者；这组负载及预热时长与前面的配对测试不同，不能混用帧率作前后对比。

|视频真实尺寸|本轮短时播放帧率|实际视频载荷|
|---|---:|---:|
|1920×1080|21.79 FPS|8.03 Mbps|
|2560×1440|21.10 FPS|15.29 Mbps|
|3840×2160|10.73 FPS|20.33 Mbps|

2K、4K 没有缩小渲染尺寸，场景 WebGL 画布在 4K 时也为 3840×2160。CSS 1920×1080、设备像素比 2 时，实测收到 3840×2160 视频，无前端脚本异常。服务器实际管线已解析为 4K 的 `bitrate=72000 max-bitrate=108000 vbv-buffer-size=7200`。原链接浏览器实际视口 2560×1238 时预算为 28 / 42 Mbps，说明动态调整按照实际宽、高生效。

上述 4K 结果尚未达到流畅大屏展示要求。RTX 3050 Ti Laptop 4 GB、WSL2、同时运行两个复杂园区实例的组合存在明确性能限制；不能承诺调整编码参数即可获得稳定 4K30。单实例、原生 Linux 和其他 GPU 的结果尚未测量。先根据实际大屏尺寸验收；需要多路稳定 4K30 时，应在最终硬件和相同并发场景复测，不能以本次 1080p 帧率替代。

还测量了 RGB 直接输入、色彩转换 4 线程、额外 CUDA 上传和较快编码预设。在这台机器的 4K 合成输入测试中，均未比当前 NV12 / P4 管线更快或更省 CPU，因此没有纳入交付版本。

简单 WebGL 点击实验，14 次点击去掉前 2 次预热，剩余平均反馈 74.98 ms；不是所有真实 3D 操作的延迟承诺。视频鼠标检测为 0 个白色鼠标像素；远端页面收到滚轮 `+120`、`-120`，顺序及方向正确；前端脚本异常为 0。证据：`quality-proof/interaction-proof.json`、`input-proof.json`。本轮没有进行相同负载的旧版延迟配对测试。

网关及 worker 镜像已通过容器健康、CPU 预加载、管理登录、账号轮换、重启与重建后的数据持久化回归。前端测试和构建、网关 Go 测试、worker 画质预算测试及实际 worker 编译均通过。服务器验收还确认原项目就绪、NVIDIA 硬件 WebGL、CPU 共享上限 100%、GPU 信息和使用率采集可用。详见 `QUALITY_VERIFICATION.json`、`quality-proof/server-proof.json`。

## 安装与大屏使用

目标服务器已先备份项目数据并保留旧镜像标签，再导入新版网关与配套 worker，重建网关。必须成套升级：仅升级网关而继续使用旧 worker，无法在调整窗口后计算新码率参数。

1. 观看页按 Ctrl+F5，加载新前端。
2. 链接选择“本机 GPU”和“自适应观看窗口”，在大屏浏览器按 F11 全屏；也可按实际屏幕尺寸选择固定分辨率。
3. 核对观看端视频真实宽、高，而不仅看浏览器窗口尺寸。4K 屏幕应收到 3840×2160；屏幕缩放设置不应导致收到较小画面后再放大。
4. 本机短时验收最高 4K。超过 4K 的屏幕仍按比例受 3840×2160 上限约束；其他 NVIDIA 型号、原生 Linux 驱动组合需在目标硬件复测。

服务器备份目录 `/root/gostream3d-backup-quality-20261009-233253/`，旧镜像标签 `gostream3d/gateway:before-gpu-quality` 与 `gostream3d/neko/nvidia-chromium:before-gpu-quality`。原项目、CPU 共享上限和 NVIDIA GPU 监控保持可用。文档不包含登录密码。
